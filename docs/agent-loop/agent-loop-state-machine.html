Agent Loop 状态机

一个 Agent 回合不是单个循环，而是三层嵌套的状态机：服务端的 run 生命周期、 SDK 的 ReAct 轮次、以及工具与子 Agent 的执行状态。它们之间只通过事件通信， 状态分别落在 Postgres、进程内存和子 runtime 里。

Overview

三层状态机，各管一段

把 Agent Loop 当成一个状态机会看不清问题，因为它的状态跨越三个生命周期完全不同的层。 每一层只向下调用，向上只通过事件反馈；没有任何一层共享另一层的内存状态。

层状态机状态存在哪负责什么
L1 调度层 queued → running → 终态 Postgres：agent_runs claim、并发、取消、超时、重启恢复、SSE 事件持久化
L2 推理层 ReAct 迭代循环 进程内存 + 事件流 上下文构建、模型调用、工具调度、停止判定、用量统计
L3 执行层 工具调用 / 子 Agent 子状态机 线程池、子 runtime、span 表 工具执行、并行批次、协作式取消、结果封装
L1 · AgentRunManager以 run 为单位调度，落库、发 SSE
→
L2 · AgentRuntime一轮 ReAct，迭代 1…max_iterations
→
L3 · ToolRegistry / SubagentTool一次工具批次，串行或并行

关键边界：L1 不认识 ReAct 的内部变量，L2 不认识 Postgres。 L2 通过 on_event 回调把 EventType 交给 L1 的 wrapper， wrapper 转成 AgentEvent 后，L1 再决定写 span、写事件表还是发 SSE。

Layer 1

Run 生命周期

L1 的状态是持久化的，因此它能在进程重启后回答“这个 run 走到哪了”。 但它目前只做到“收尾”，不做“续跑”：重启后残留的 running 会被收敛成 interrupted。

单副本假设：RunConfig.lease_seconds 目前只定义未使用， 服务启动时会无条件接管所有 running run。多副本部署会重复执行； 在引入 lease 回收之前，不要把 agent worker 扩到两个进程。

Layer 2

ReAct 循环

L2 是真正推进任务的状态机。它不是“一次模型调用”，而是最多 max_iterations 轮的循环：每轮构建上下文、问模型、执行本轮的 工具批次、把结果写回上下文，然后进入下一轮。停止条件只有五类：正常作答、 长度/内容过滤、步数耗尽、无进展、取消。

图可横向滚动查看完整循环。

一轮迭代的完整步骤

  1. 初始化。规范化输入、确定 session_id、重置子 Agent 预算与台账、创建上下文、压缩器、ledger、progress guard。
  2. 取消检查。进入本轮前检查 cancel_event。
  3. 构建请求。拼上下文，必要时压缩，注入运行时提示，发出 MODEL_REQUEST。
  4. 模型调用。流式或非流式；合并 usage；发出 MODEL_RESPONSE。
  5. 写回助手消息。把 assistant 消息加入上下文和 new_messages；记录本轮的 tool_calls。
  6. 取消检查。模型响应已完整，执行工具之前再检查一次。
  7. 无工具调用。把 finish_reason 映射为 final / length / content_filter，结束循环。
  8. 声明全部调用。先为每个 tool_call 发 TOOL_CALL，让前端能同时显示 running。
  9. 执行批次。连续的 concurrency_safe 调用可并行，其余作为串行屏障。
  10. 回放结果。按声明顺序处理 ledger、guard、TOOL_RESULT 和 tool 消息；每批结束后再做一次取消检查。
  11. 守卫停止。如果 guard 判定无进展，在轮次之间停止，进入 tool-free 最终作答。

停止原因与最终状态

stop_reason触发SDK 结果服务端 run
final模型正常作答，无工具调用RunResultcompleted（有内容）
length / content_filterprovider 截断或内容过滤RunResult有内容则 completed；空内容则 failed
max_iterations步数耗尽可先做一次 tool-free 作答；否则抛 MaxIterationsExceeded有内容 completed；否则 failed（wrapper 映射为 agent_upstream_error）
no_progress连续工具调用没有新证据可先做一次 tool-free 作答；否则抛 NoProgressError有内容 completed；否则 failed（agent_no_progress）
cancelledcancel_event 在安全点命中抛 RunCancelled，异常上挂 partial resultcancelled

取消检查点

check_cancelled() 只在安全边界调用，保证助手消息与工具消息始终成对：

  • 每轮迭代开始前；
  • 模型响应完整、工具执行之前；
  • 每个工具批次结束后、下一批或下一轮之前；
  • 步数耗尽、进入 tool-free 最终作答之前；
  • 无进展停止、进入 tool-free 最终作答之前。

不在流式 token 循环内部检查。否则会留下半截 assistant 消息， 破坏下一轮的消息协议。取消的代价是“等到当前模型流结束或当前工具返回”。

失败路径

# 伪代码：循环的骨架
for iteration in 1..max_iterations:
    check_cancelled(iteration)
    messages = context.build()
    response = model(messages)                    # MODEL_REQUEST / MODEL_RESPONSE
    pending_calls = response.tool_calls
    check_cancelled(iteration)

    if not pending_calls:
        stop_reason = map_finish_reason(response)
        break

    announce_all(pending_calls)                   # TOOL_CALL ×N
    results = invoke_many(pending_calls, cancel_event)
    for call, result in zip(pending_calls, results):
        apply_to_context(call, result)
        emit_tool_result(call, result)             # TOOL_RESULT ×N
    pending_calls = []
    check_cancelled(iteration)

else:
    # 步数耗尽：先尝试一次不带工具的作答
    if not tool_free_answer():
        persist_failed("max_iterations")
        raise MaxIterationsExceeded

协议不变量：每个 assistant 的 tool_call 必须有配对的 tool 消息。 取消、异常、步数耗尽时，_abort_pending_tool_calls 会给未执行的调用补一条 {"error": "run aborted: ..."}，否则下一次对话会把残缺历史发给模型。

Layer 3

工具执行状态机

工具状态挂在每个 tool_call_id 上，而不是整个 run 上。一次模型响应里的 N 个调用可以处在不同状态：已声明、执行中、完成、失败或中止。

状态产生方式可见位置
declared模型返回 tool_calls 后，先统一发 TOOL_CALLagent_run_events、tool span
running批次开始执行tool span status=running
completed工具返回，is_error=falsetool span、TOOL_RESULT
failed工具返回，is_error=truetool span、TOOL_RESULT
aborted取消时未开始或被丢弃的调用metadata.aborted=true 的结果

批次调度

  • invoke_many 把连续、声明了 concurrency_safe=True 的调用合成一批并行执行。
  • 任何非并发安全的调用都是单调用批次，同时是前后屏障：前一批必须结束，后一批才能开始。
  • 返回列表始终与声明顺序一致，即使完成顺序不同。
  • 子 Agent 工具默认是写类型（effect=write），因此是串行屏障。

取消时的工具语义

并行批次

  • 每 0.2 秒轮询 cancel_event；
  • 已完成的 future 保留结果；
  • 未开始的 future 调 cancel()；
  • 没有结果的槽位补 aborted ToolResult。

串行工具

  • 执行期间不轮询取消；
  • 必须等工具自己返回；
  • 副作用已经发生，不能回滚；
  • 取消延迟等于当前工具剩余时间。

结果可能被丢弃，副作用不会。取消后，已开始工具的结果可能不写入上下文， 但它对文件、网络或 shell 的影响已经存在。恢复/重试时必须按 at-most-once 处理。

Layer 3

子 Agent 状态机

子 Agent 在父 Agent 看来就是一个普通工具调用：一次 tool.call， 一次 tool.result。但在内部，它是一个独立的 ReAct runtime，拥有自己的 上下文、工具白名单、轮次预算和取消事件。

状态含义父 Agent 看到的span 状态
started委派开始，子 runtime 创建tool call runningrunning
completed子 Agent 正常作答tool result，is_error=falsecompleted
partial截断或步数耗尽但有内容tool result，is_error=true（视情况）completed
failed子 runtime 异常或无内容tool result，is_error=truefailed
timeout子 Agent 自己的计时器触发tool result，is_error=truefailed
cancelled父取消镜像到 child_canceltool result，is_error=trueaborted

两个独立的中止源

  • 父取消镜像：每个委派创建新的 child_cancel；一个 daemon watcher 每 50 毫秒轮询父事件，命中就置位。嵌套委派逐层镜像。
  • 子 Agent 超时：threading.Timer 在 default_timeout_seconds 后置位同一个 child_cancel，并单独记录 timed_out 用于区分原因。

子 Agent 在安全点退出后，RunCancelled 带着 partial RunResult 返回；SubagentTool 把它归一化成结果信封，父 Agent 继续自己的循环。 父是否也停下，取决于父自己的 cancel_event，子 Agent 不会反向取消父。

可恢复性：只有 completed / partial 且最后一条是 assistant 消息的子会话才标记 resumable=true。取消、超时、失败都不保留 resume 会话；父 Agent 只能看到有损的结果信封。

Observability

Span 状态机

Span 是 run 的旁路状态机，不参与调度。它的职责是把“发生了什么”变成可查询的树， 并保证取消、崩溃后不会留下永远 running 的行。

span 状态何时写入来源
running模型请求、工具调用、子 Agent 开始MODEL_REQUEST / TOOL_CALL / SUBAGENT_STARTED
completed模型响应、工具结果成功、run 正常结束MODEL_RESPONSE / TOOL_RESULT / finalize
failed工具错误、run failedTOOL_RESULT(is_error) / finalize
aborted取消或 run cancelledabort_open / finalize
interrupted服务关闭或崩溃恢复settle_open_spans

run 状态到 span 状态的映射是固定的：completed → completed、 failed → failed、cancelled → aborted、 interrupted → interrupted。写入按 (run_id, span_id) 幂等 upsert， 已终态的行不会被迟到的重复事件重新打开。

采集不是必然的：AGENT_SPAN_CAPTURE 关闭或采样未命中时， 整个 run 不写 span；eval 会因为没有 span 拒绝评分。取消/恢复逻辑不能依赖 span 存在。

Signal path

取消信号怎么传

取消是协作式的：前端发一个 HTTP 请求，服务端置位一个进程内的 threading.Event，执行层在各自的安全点轮询。没有任何地方强杀线程。

1 · 前端POST /agent/runs/{id}/cancel，不主动断开 SSE
→
2 · Manager写 cancel_requested_at，cancel_event.set()
→
3 · Wrapper每 0.5 秒轮询，抛 agent_cancelled
4 · SDK安全点命中 → _cancel_run
→
5 · 工具 / 子 Agent批次 0.2 秒轮询；子 Agent watcher 50 毫秒镜像
→
6 · Finalizeflush、abort open、写消息、finish(cancelled)

三种取消路径

run 状态行为结果
queuedcancel_queued 直接改状态，不启动 workercancelled + error / done 事件
running（进程内有 task）只写时间戳并置位 Event，不 task.cancel()执行层在安全点退出，finalize 为 cancelled
running（进程内无 task）_finalize_orphan_cancel 直接收尾cancelled，补齐 open 工具的 aborted 结果

关流不等于取消。background 模式下断开 SSE 不会停止 run，客户端用 run_id + after_seq 重连即可续看。只有显式 cancel 请求才会停。 legacy 模式（AGENT_RUN_BACKGROUND=false）是例外：断流会取消本地 task。

“用户取消”和“服务关闭”是两种终态：前者是 cancelled / agent_cancelled，后者是 interrupted / agent_interrupted。它们在前端的显示和重试语义不同。

Durability

重启与恢复

当前实现能恢复“现场”，不能恢复“执行”：重启后残留的 running 会被收敛成 interrupted， 已生成的内容和工具 trace 会保留，但 ReAct 循环不会接着跑。理解恢复需要区分三件事： 中断时写什么、启动时怎么收尾、下一轮从哪里读上下文。

三种中断

场景谁收尾run 终态助手消息
用户取消_finalize(cancelled)cancelledcancelled，保留 tool_trace
优雅关闭_finalize(interrupted)interruptedfailed（消息状态只有 completed/cancelled/failed）
崩溃 / SIGKILL下次 startup() → _recover_runinterrupted（或按已有消息推断）failed，或沿用已经写好的消息

恢复步骤

  1. startup() 读取所有 running run。
  2. _recover_run 读取 run、用户消息、助手消息。
  3. 按助手消息是否存在推断 span 终态，settle_open_spans 关闭仍 running 的 span。
  4. 从 partial_content 和 partial_metadata 重建 writer 的内存态。
  5. _abort_trace_entries 把 running 的工具条目改成 aborted，并补写 tool.result。
  6. 写助手消息（通常 status=failed），把 run 标成 interrupted。
  7. 补 error 事件，publish done。

优雅关闭 vs 崩溃：优雅关闭时 _finalize(interrupted) 在进程退出前完成， 不进入恢复；崩溃时 run 停留在 running，直到下次启动才被收敛。

现场存在哪，下一轮读什么

数据位置写入时机下一轮读取

助手消息conversation_messages只在终态写是，唯一上下文来源

下一轮请求走 _prepare_turn → build_history，只读 conversation_messages。 agent_runs 的角色是在收尾时把现场补写进这张表，之后不再参与 prompt； agent_run_events 和 agent_run_spans 都不进入模型上下文。

下一轮实际看到什么

  • 用户消息：status=completed 才加入；
  • 已完成助手消息：正文 + tool_trace 展开成 assistant(tool_calls) + tool 结果 + 最终回答；
  • 取消 / 失败的助手消息：只展开 tool_trace，不把半截回答当成助手答案；
  • 没有 tool_trace 的取消 / 失败消息：整条跳过。

中断时生成的半截回答只展示给用户，不会进入下一轮 prompt。 恢复出来的上下文 = 用户消息 + 历史已完成回答 + 中断轮次里已经执行过的工具调用和结果。

记忆是独立的上下文来源：AgentMemoryRecall 从工作区 Markdown / 索引注入， 不来自这些 run 表。

助手消息是“收尾进度”的代理信号

_finalize 先 insert_assistant_message，再 repo.finish， 两次写是独立事务。因此“消息是否存在”能反推崩溃发生在收尾的哪一步：

崩溃点run 行助手消息恢复判断
执行中，或收尾还没写消息running不存在按 interrupted 收尾
消息已写、run 尚未终态running存在以消息里的状态为准
repo.finish 之后终态存在或不存在不再进入恢复

状态精度：interrupted 和 failed 在助手消息里都存成 failed。 如果要求精确恢复，应优先读消息 meta 里的 run_status，而不是只看 status。

如果要“接着跑”

需要 checkpoint，记录 ReAct 的位置而不是只记录输出。最小设计：

  • 存什么：phase、iteration、new_messages、工具结果摘要、usage、ledger/guard 计数、子 Agent 会话；
  • 放哪：新增 agent_run_checkpoints，按 (run_id, seq) 唯一，大输出引用事件 seq；
  • 何时写：模型响应后、每个工具批次后、子 Agent 返回后；
  • 怎么恢复：校验消息协议与 harness 版本，从下一个安全边界继续；
  • 一致性：有副作用的工具默认 at-most-once；执行中的调用标 aborted，不盲目重放。

Guarantees

不变量与失败模式

必须成立的不变量

  • 每个会话最多一个活跃 run。由部分唯一索引保证 queued / running 唯一。
  • 事件序号单调。append_event 在 last_seq >= seq 时返回 false，重复写不会生效。
  • 工具调用与结果配对。取消或异常时由 _abort_pending_tool_calls 补齐。
  • 终态不可回退。run 的 finish 只更新 queued / running；span 的终态不会被迟到事件重新打开。
  • 助手消息只在终态写。运行中只更新 partial_content 和事件表。
  • 取消只在安全点生效。不在流式 chunk 内部中断。
